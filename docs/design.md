# Design

전북대학교 및 컴퓨터인공지능학부의 공지를 주기적으로 확인하고, 새 공지 중 사용자에게 중요한 정보를 Discord로 전달한다. 여러 게시판을 직접 반복해서 확인하는 수고를 줄이는 것이 목표다.

구현 언어는 Python이다. 설계 결정과 이유는 [decisions.md](decisions.md)에 기록한다.

## 대상 공지

초기 지원 대상은 전북대학교 홈페이지와 컴퓨터인공지능학부 홈페이지 공지다. 개발은 하나의 전북대학교 게시판부터 시작하며, 새로운 출처는 필요에 따라 추가한다.

## 전체 처리 흐름

```text
공지 게시판 → Collector → 원본 응답 → Parser → Notice[]
          → Detector → 신규 공지 → Classifier → 관련 공지 → Notifier
```

처리 결과와 이미 확인한 공지의 상태는 Storage에서 관리한다.

## Notice 모델

서로 다른 게시판의 공지를 공통 Notice 형태로 변환한다. 초기 필드는 다음과 같다.

| 필드 | 의미 |
| --- | --- |
| `id` | 공지 고유 식별자. 가능하면 게시판의 게시물 ID를 사용한다. |
| `source` | 공지 출처. 예: `jbnu`, `csai` |
| `title` | 공지 제목 |
| `url` | 공지 원문 URL |
| `published_at` | 공지 게시일 |

본문과 첨부파일 등은 필요성이 확인되면 추가한다.

## 컴포넌트

### Collector

HTTP 요청으로 게시판의 원본 응답을 가져와 Parser에 전달하고, 네트워크 오류를 처리한다. HTML 해석이나 중요도 판단은 담당하지 않는다.

### Parser

원본 응답에서 공지 목록과 게시물 ID, 제목, URL, 게시일을 추출해 Notice로 변환한다. 사이트별 HTML 구조 차이는 각 사이트에 대응하는 Parser에서 처리한다.

### Detector

Notice를 이전에 처리한 공지와 비교해 신규 공지를 판별한다. 같은 공지를 반복해서 신규로 처리하지 않도록 한다.

### Classifier

신규 공지의 중요도와 사용자 관련성을 판단한다. 공모전, 해커톤, 경진대회, 장학, 인턴·취업, 학사상 확인이 필요한 공지를 우선 고려한다.

분류 방식은 구현 과정에서 결정하며, 필요하면 규칙 기반 방식과 LLM 기반 방식을 함께 사용하는 것도 고려한다.

### Notifier

중요하다고 판단된 신규 공지를 Discord로 전달한다. 알림에는 최소한 제목, 출처, 원문 링크를 포함한다.

### Storage

이미 확인한 공지와 실행에 필요한 상태를 저장해 신규 공지 판별과 중복 알림 방지를 지원한다. 저장 방식은 구현 과정에서 결정한다.

## 실패 처리 원칙

- 수집, 파싱, 저장, 알림 전송 중 일부가 실패해도 기존 상태가 손상되지 않아야 한다.
- 수집이나 파싱에 실패한 데이터를 정상 처리된 공지로 기록하지 않는다.
- 재시도와 복구 정책은 구현 과정에서 결정한다.

## 실행 방식

초기에는 수동으로 실행하고, 최종적으로 수집 → 파싱 → 신규 판별 → 분류 → 알림 → 상태 저장을 주기적으로 자동 실행한다. 자동 실행 주기와 실행 환경은 핵심 기능 구현 이후 결정한다.

## 개발 단계

1. **단일 출처 수집**: 하나의 전북대학교 게시판에서 원본 데이터를 가져와 Notice로 변환한다.
2. **신규 공지 판별**: 이전 실행 상태와 비교해 새 공지를 찾는다.
3. **여러 출처 지원**: 컴퓨터인공지능학부를 포함한 여러 게시판을 같은 흐름으로 처리한다.
4. **분류**: 신규 공지의 중요도와 사용자 관련성을 판단한다.
5. **알림**: 중요한 신규 공지를 Discord로 전달한다.
6. **자동화**: 전체 파이프라인을 주기적으로 실행한다.

## Open Questions

필요성이 명확해졌을 때 결정한다.

- 주요 라이브러리, Notice 모델의 최종 필드
- 상태 저장 방식, 중요도 분류 방식, LLM 사용 여부와 모델
- 자동 실행 주기, 배포 환경
- 로깅 방식, 재시도 정책

## 설계 원칙

먼저 동작하는 작은 시스템을 만들고, 필요하기 전에는 복잡한 추상화를 추가하지 않는다. 각 컴포넌트는 명확한 책임을 가지며, 사이트별 처리와 공통 로직을 분리해 새 출처를 추가하기 쉬운 구조를 지향한다. 중요한 설계 변경은 이유를 기록한다.
