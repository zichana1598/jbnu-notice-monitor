# Design

## 1. 프로젝트 목표

전북대학교 및 컴퓨터인공지능학부의 공지사항을 주기적으로 확인하고,
새롭게 게시된 공지 중 사용자에게 중요한 정보를 선별하여 Discord로 전달한다.

사용자가 여러 공지 게시판을 직접 반복해서 확인해야 하는 문제를 줄이는 것을
이 프로젝트의 목적으로 한다.


## 2. 대상 공지

초기 지원 대상은 다음과 같다.

- 전북대학교 홈페이지 공지
- 컴퓨터인공지능학부 홈페이지 공지

새로운 공지 출처는 필요에 따라 추가한다.


## 3. 전체 처리 흐름

    Notice Board
        ↓
    Collector
        ↓
    Raw Response
        ↓
    Parser
        ↓
    Notice[]
        ↓
    Detector
        ↓
    New Notice[]
        ↓
    Classifier
        ↓
    Relevant Notice[]
        ↓
    Notifier

처리 결과와 이미 확인한 공지에 대한 상태는 Storage를 통해 관리한다.


## 4. Notice 모델

서로 다른 게시판에서 수집한 공지는 내부적으로 공통된 Notice 형태로 변환한다.

초기 Notice 모델은 다음 필드를 가진다.

    id
    source
    title
    url
    published_at

### id

공지의 고유 식별자.

가능하면 각 게시판에서 제공하는 게시물 ID를 사용한다.

### source

공지가 수집된 출처를 나타낸다.

예:

    jbnu
    csai

### title

공지 제목.

### url

공지 원문 URL.

### published_at

공지 게시일.

본문, 첨부파일 등의 데이터는 필요성이 확인되면 이후 추가한다.


## 5. 컴포넌트

### 5.1 Collector

공지 게시판으로부터 원본 데이터를 가져온다.

주요 책임:

- HTTP 요청
- 응답 수신
- 네트워크 오류 처리

Collector는 HTML을 해석하거나 공지의 중요도를 판단하지 않는다.

출력된 원본 데이터는 Parser로 전달한다.


### 5.2 Parser

Collector가 가져온 원본 데이터를 분석하여 공통 Notice 형태로 변환한다.

주요 책임:

- 공지 목록 추출
- 게시물 ID 추출
- 제목 추출
- URL 추출
- 게시일 추출

사이트별 HTML 구조 차이는 각 사이트에 대응하는 Parser에서 처리한다.


### 5.3 Detector

Parser가 생성한 Notice와 이전에 처리한 공지를 비교하여
새로운 공지를 판별한다.

동일한 공지가 반복해서 신규 공지로 처리되지 않도록 한다.


### 5.4 Classifier

신규 공지가 사용자에게 얼마나 중요한지 판단한다.

우선적으로 고려할 공지의 예시는 다음과 같다.

- 공모전
- 해커톤
- 경진대회
- 장학
- 인턴 및 취업
- 학사상 확인이 필요한 공지

구체적인 분류 방식은 구현 과정에서 결정한다.

필요한 경우 규칙 기반 방식과 LLM 기반 방식을 함께 사용하는 것도 고려한다.


### 5.5 Notifier

중요하다고 판단된 신규 공지를 사용자에게 전달한다.

초기 알림 채널은 Discord를 사용한다.

알림에는 최소한 다음 정보를 포함한다.

- 공지 제목
- 공지 출처
- 원문 링크


### 5.6 Storage

시스템 실행에 필요한 상태를 저장한다.

주요 목적:

- 이미 확인한 공지 기록
- 신규 공지 판별
- 중복 알림 방지

구체적인 저장 방식은 구현 과정에서 결정한다.


## 6. 실패 처리 원칙

공지 모니터링 과정의 일부가 실패하더라도
기존 상태가 손상되지 않아야 한다.

고려해야 할 실패 상황의 예시는 다음과 같다.

- 사이트 접속 실패
- HTTP 오류
- HTML 구조 변경
- 파싱 실패
- 저장 실패
- Discord 알림 전송 실패

특히 수집 또는 파싱에 실패한 데이터를
정상적으로 처리된 공지로 기록해서는 안 된다.

구체적인 재시도 및 복구 정책은 구현 과정에서 결정한다.


## 7. 실행 방식

최종적으로 전체 파이프라인을 일정 주기로 자동 실행한다.

    Scheduled Execution
            ↓
        Collect
            ↓
         Parse
            ↓
         Detect
            ↓
        Classify
            ↓
         Notify
            ↓
        Persist

초기 개발 단계에서는 수동으로 실행한다.

자동 실행 주기와 실행 환경은 핵심 기능 구현 이후 결정한다.


## 8. 개발 단계

### Milestone 1 — Single Source Collection

하나의 전북대학교 공지 게시판에서 원본 데이터를 가져오고,
공지 목록을 Notice 형태로 변환한다.

### Milestone 2 — New Notice Detection

이전 실행 상태와 비교하여 새로운 공지를 판별한다.

### Milestone 3 — Multiple Sources

컴퓨터인공지능학부를 포함하여
여러 공지 게시판을 동일한 처리 흐름에서 지원한다.

### Milestone 4 — Classification

신규 공지의 중요도 및 사용자 관련성을 판단한다.

### Milestone 5 — Notification

중요한 신규 공지를 Discord로 전달한다.

### Milestone 6 — Automation

전체 파이프라인을 주기적으로 자동 실행한다.


## 9. 설계 결정

### Collector와 Parser 분리

Collector와 Parser는 별도의 컴포넌트로 구성한다.

Collector는 원본 데이터 수집만 담당하고,
Parser는 수집된 데이터를 Notice 형태로 변환하는 역할만 담당한다.

이를 통해 네트워크 통신과 데이터 해석을 분리하고,
Parser를 독립적으로 테스트하거나 교체할 수 있도록 한다.

사이트별로 별도의 Collector가 필요한지는 현재 확정하지 않는다.
단순한 HTTP 요청으로 동일하게 데이터를 가져올 수 있다면
공통 Collector를 사용하고 Parser만 사이트별로 분리할 수 있다.


## 10. 미결정 사항

현재 단계에서 의도적으로 결정하지 않은 항목은 다음과 같다.

- 프로그래밍 언어 및 주요 라이브러리
- Notice 모델의 최종 필드
- 상태 저장 방식
- 중요도 분류 방식
- LLM 사용 여부 및 모델
- 자동 실행 주기
- 배포 환경
- 로깅 방식
- 재시도 정책

각 항목은 실제 구현 과정에서 필요성이 명확해졌을 때 결정한다.


## 11. 설계 원칙

- 먼저 동작하는 작은 시스템을 만든다.
- 필요하기 전에는 복잡한 추상화를 추가하지 않는다.
- 네트워크 통신과 데이터 해석을 분리한다.
- 사이트별 처리와 공통 처리 로직을 분리한다.
- 각 컴포넌트는 하나의 명확한 책임을 가진다.
- 새로운 공지 출처를 추가하기 쉬운 구조를 지향한다.
- 동일한 공지를 중복 처리하거나 중복 알림하지 않는다.
- 실패로 인해 기존 상태가 손상되지 않도록 한다.
- 중요한 설계 변경에는 결정 이유를 기록한다.
